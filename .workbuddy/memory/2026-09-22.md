### 🔴 我上一轮对所有者说错的话（必须记在明处）

我说"重跑同一条命令即可续跑，幂等"。**那句话当时不成立。**
原实现对"已跑满的臂"`raise SystemExit` ⇒ 多臂 campaign 会**在第一个跑完的臂上中止**。
于是 A/B 早已完成，C 在进程死掉后**没有任何 driver 能接上它**，`campaign_report.json` 也从未生成。

- **修**：引入 `ArmAlreadyComplete`；campaign 层**跳过并记录** `arms_status`；`--fresh` 是唯一重做通路。
- **回归** `test_a_finished_arm_is_skipped_so_a_campaign_can_be_re_run`：同一条命令复跑 ⇒
  `arms_status == {B: already_complete, C: already_complete}`、`failed_arms == []`，
  且 C 的 `session_id` **逐字不变**（证明没被偷偷重跑）。
- **实测续跑生效**：重启后输出
  `[A] already_complete … skipping` / `[B] already_complete … skipping` / `[C] start`，C 随即继续。

### 🔴 第二个缺陷：`--fresh` 在 Windows 上必崩

归档旧报告的文件名用了 `_utc_now()`，含 `:` ⇒ `OSError [WinError 123] 文件名、目录名或卷标语法不正确`。
**是上面那条新写的测试当场抓到的**——此前 `--fresh` 路径**从未被执行过**，所以这个崩溃一直躺着。
修：新增 `_stamp_for_filename()`（`:` → `-`），JSON 字段仍用 `_utc_now()`。

### 可复用教训（已入 MEMORY §4）

1. 「幂等重跑」这类承诺**必须用测试证明，而且要证多臂情形**——单臂测试全绿挡不住 campaign 层中止。
2. **时刻进文件名要换安全字符集**：`:` 在 Windows 非法。
3. 长跑的 driver 要**分臂记状态**（`arms_status`），否则"哪一臂停了"只能靠翻进度流猜。
4. **报速率报中位窗口，不报累计**（累计把一次性扰动永久计入，看起来像模型性质）。
5. 空窗口的指标写 `null`，**不写 `0.0`**（0.0 会被读成塌陷）。
