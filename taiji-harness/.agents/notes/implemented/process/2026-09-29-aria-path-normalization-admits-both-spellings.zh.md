# Agent Note: ARIA 路径归一化同时认两种拼写

Status: implemented

[English](2026-09-29-aria-path-normalization-admits-both-spellings.md) | 中文

## 问题

比对可访问性树快照的浏览器 lane 会把抓到的工作区路径归一化成 `{{cwd}}` 记号。归一化函数是按"分隔符原生"的路径字符串做切分的，而 ARIA 快照会把每个反斜杠转义，于是 Windows 上这次切分永不命中：路径留在抓到的文本里，只有末尾的 basename 被换成记号。已入库的金样是在路径不含反斜杠的环境里录的，因此里面就是裸的 `{{cwd}}` ⇒ 同一条 lane 在 Windows 读起来像"金样不符"，在 Linux 却通过——此前被报成一处解释不了的差异，而不是归一化缺陷。

## 裁定

`apps/web/tests/scaffold.ts` 的 `normalizeAria` 先替转义拼写、再替原生拼写，两者都映射到 `{{cwd}}`。POSIX 下两个串相同，第二次替换是无操作，抓到的输出与 Linux 原有产出逐字节一致；Windows 上第一次替换现在能够命中路径。验收**没有改动金样**：受影响那条 lane 在 replay 模式通过，另外两条本轮未重录的 lane 仍通过——这正是"新增步骤对 POSIX 无操作"的证据。

重录后的金样保持 Linux 形状，因为基线持有的是记号而非宿主路径。若在本次修复之前重录，就会把一个只有 Windows 才成立的拼写烤进入库基线，让这条 lane 在下一种平台上失败——这与更早一份对分隔符敏感的夹具暴露的是同一失效形态。

## 考虑过的替代方案

- **重录受影响的金样。** 能压掉一条 lane，但把宿主特有的快照写进入库基线，等于把失败搬到别的平台而不是消除它。与"分隔符敏感夹具不能在单台机器上刷新"同一条理由否决。
- **比较前把路径统一成正斜杠。** 更短，但会重写页面确实渲染出来的分隔符，削弱的是整棵树里所有路径形状的行，而不只是工作区根那一条。
- **在 Windows 上 skip 这条 lane。** 恰好移除唯一能观察到缺陷的平台；本仓的平台上 skip 只用于功能本身不可用的情形。

## 后果

"从可访问性树里读工作区路径"这一类 lane 现在平台中立，任何平台录的金样都能在所有平台校验。代价是留给后续归一化工作的一条常则：当被捕获的表示会转义宿主串里真实存在的字符时，同一次记号替换必须同时认两种拼写，并且 POSIX 那一侧要**证成**无操作而不是默认无操作。除这条常则之外，没有任何上线格式、被捕获的载荷或已入库金样发生变化。
