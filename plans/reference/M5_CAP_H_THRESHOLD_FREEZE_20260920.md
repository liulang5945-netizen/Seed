| 项 | 规则 |
|---|---|
| 阈值形态 | 各读数的 `max × 2`（安全系数 2.0） |
| 采样条件 | 机器空闲、≥5 次重复、每次**新建进程**、显式 `relax_legacy_guard + constrained_decode`（与正式评价同链路） |
| 绑定范围 | **(设备, 链路, checkpoint)** 三元组。三者任一改变 ⇒ 本件阈值作废，必须重采重冻 |

| 判据接线 | `judge_health` 在读任何 H 字段之前先校 `chain == REQUIRED_CHAIN`（既有守卫，不改） |

## §3 生效时点（关键，不得跳过）

**§2 的四个数值不随本件生效。** 同一轮的所有者裁决把默认基座换成 16M-tick 训练态，而阈值按 §1 绑定 `(设备, 链路, checkpoint)` 三元组 ⇒ 换底之后必须在新基座上重跑一次 `calibrate_taiji_cap0_h_gates.py --repeats 5`，把新分布写进本件 §4 并声明生效。在此之前，CAP 与 J4 的 H 支仍记 `partial`（"不可留空就宣布通过"）。

这条顺序不是形式主义：本轮已经实测到 **H 读数依链路而定**（同一 checkpoint 裸链 H02 0.3223 s / H04 163,511 B，required 链 H02≈0.49 s / H04≈211,000 B）。若把旧链路口径的阈值冻到新基座或新链路上用，门限一上线就是错的——要么长期误判劣化，要么永久放行劣化。
