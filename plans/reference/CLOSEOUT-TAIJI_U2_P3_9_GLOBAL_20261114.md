## 3. 行为窗为什么不能判优劣（逐条如实）

1. **成本配平不可达**：A 臂 0.25 CPU、B 臂 0.1562 CPU，`ratio=1.6005` 超出冻结带。这是两图的**真实结构性计算量差异**（A 有 H 递推与 `w_g` 投影，B 更轻），不是读数错误。本机 `process_time` 分辨率 0.0156 s，两臂绝对量都只有 10–16 个 tick，**低 CPU 下 ratio 分辨率不足**必须随读数引用。
2. **即使配平也无优劣证据**：配对 bootstrap 2000 次 Δ=0.03125、CI 覆盖 0，按 `decision_rule` 只会落 `inconclusive_within_window`；审计的红方向把 `cpu_ratio` 修进带后重算正是这个结论。
3. **无已验旧能力**：保持不签（`no_verified_old_capability`）；合成合法输入窗不是自然中文／项目任务，0 能力声称。
4. **不加剂量、不改门值、不重跑挑数**：按冻结出口结案。`budget_cannot_express` 也不适用（两臂 loss 有动态范围），更不构成把 64 次扩到 2303 次的理由。

## 4. 必须随结论登记的两处实现事实

- **A readout 的 group 维**：首版 A 输出为 `[T,G,4]`，与 B 的 `[T,4]` 不同维，导致恢复阶段的交叉熵无法比较。改为对 group 维取均值后经 H 读出（`[T,4]`），**修实现以符合合同，判据一字未改**；图验收在修复后重跑一次，19/19 结论不变，旧报告未入库、未引用。
- **B 的合法内容门与逐参数信用**：首版 B 直读原始 `z/a`，把门全置 0 时输出不变，且 `units.p` 完全无梯度。改为「门控后的单位活动经 `p` 投影再直接查询」，既让合法性门真正生效，又使每个声明参数都有梯度。**这是实现缺陷修复，不是为通过而放宽检查**；契约测试同时保留红方向（切断单位路径后 `units.r` 梯度归零）。
