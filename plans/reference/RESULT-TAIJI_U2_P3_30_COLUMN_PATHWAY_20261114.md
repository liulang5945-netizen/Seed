# 结果卡：22.5.P3.30 列结构观测通路（`column-observation-v1`）与它的读出验证

日期 2026-11-14 ｜ 取证基线 `de24a24fd` ｜ 卡片出口 `column_tokens_too_lossy` ｜ 0 能力声称

## 0. 一句话

给主体加了一条**零参数**的列观测通路（同一套编码器按列重分组，`state_dict` 一字未动），并用 P3.28 的读出验证：**颜色能过（分类 0.812）、位置过不去（列命中 1/24、四向 0.3125）**。8 维列 token 把一列的颜色构成压得太狠，撑不起"到原型的距离"这种几何。

## 1. 主体侧改动（零参数）

`taiji/u2_observation_columns.py`，身份 `column-observation-v1`：

| 接口 | 作用 |
|---|---|
| `column_values(patches)` | [16,48] patch → [16,48] 列；列 k = 块列 `k//4`、块内列 `k%4`，跨 4 个块行读取 |
| `column_coordinates(coords)` | 列坐标（x 取列中心、y=0，帧槽位原样保留） |
| `column_tokens(subject, obs, coords)` | 用主体**自己的** `encoder.rgb`／`metadata`／`modality` 跑列，返回 [16,8] |

关键事实：**一列也是 48 个值**（16 行 ×3 通道），与 patch 同宽，所以同一个 `encoder.rgb`（48→8）可以吃列——不需要新参数、不需要新权重。

**旧 bundle 不受影响的证据**：`make_model('native')` 仍是 **22,742 参数／194 张量**（守卫里逐次断言）；契约测试 9 项全绿，含"列 k 必须等于图像第 k 列""错误重排必须被抓到""主体 `state_dict` 在调用前后逐键相等"。

## 2. 零训练可行性核验（决定这张卡值不值得跑）

7 类颜色线性探针（每位置一个样本，train 1024／fit 512，岭回归）：

| 表示 | train | **fit** |
|---|---:|---:|
| 主体 patch token（现行 4×4 块，8 维） | 0.385 | **0.387** |
| 主体 token **按列重分组**（同参数，8 维） | 0.690 | **0.674** |
| 原始列像素（48 维，上界） | — | 1.000 |

⇒ **粒度确实是问题**（0.387→0.674；但这两个数都在"全判背景"的 0.746 之下，见文末更正），但列 token 仍离上界很远，所以判据里把"token 太有损"预注册成一个正常出口，而不是事后解释。

## 3. 读出验证（单变量：特征空间换成列 token）

| 剂量 | train | fit | 颜色（fit） | 列命中 | 未知 8 | 误弃权 |
|---:|---:|---:|---:|---:|---:|---:|
| 1844 | 0.301 | 0.281 | 0.375 | 1/24 | 0 | 0 |
| 3688 | 0.289 | 0.281 | 0.750 | 1/24 | 0 | 0 |
| 7376 | 0.293 | **0.3125（10/32）** | **0.8125** | **1/24** | 0 | 0 |

出口 `column_tokens_too_lossy`（fit ≤ 0.55）。可学参数只有 **59**（6 路分类器 54＋4 个标量＋温度），六色原型是编码器对"整列涂成该色板色"的固定输出，不参与学习。

## 4. 判读

1. **列重分组解决了"颜色"，没解决"几何"**：分类器从列 token 里能认出 0.812 的颜色（高于 7 类随机 0.143 很多），但"这一列有多像色板色 c"的距离在 8 维 tanh 空间里不再保序——一列只有少数像素是目标色、其余是背景，token 是混合，距离排序与颜色占比脱钩。
2. **不能据此说主体学不会**：这条卡只测了"固定原型距离"这一种读出几何。测到的是**信息量足够、几何不匹配**，而这两件事的修法不同（前者要加宽编码器，后者要换读出）。
3. 与 P3.28 的对照很清楚：同一读出在原始像素上是 0.969，在 8 维列 token 上是 0.3125——**差距就是那 40 维被丢掉的信息**。

## 6. 唯一的下一步（需要所有者点头）

这条卡把问题切成了两半，下一半是**参数**：列编码仍是 8 维，而 P3.28 证明 3 通道原始像素（48 维/列）够用。加宽列编码器（8 → 24 或 32）会给主体**新增参数**，因而是新候选身份、需要新的 bundle，旧 bundle 仍然不受影响但会形成两条身份谱系。

**是否立项 `22.5.P3.31`——列编码器加宽（8 → 32）作为新候选身份 `native+columns32 v1`，其余（数据、剂量、读出、判据）不变，验证 fit 能否从 0.3125 抬到 0.80？**

若批准：先零训练可行性核验（同一 7 类探针在该宽度下能否接近 1.000），再定价、冻结、执行。若不批准：检测器线与列通路就停在这里，结论写成"8 维列 token 信息量不足，需要更宽的空间编码"，作为架构级缺口存档。

## 更正（2026-11-14，P4.1 结案后）

上表的 7 类探针读数**缺一个下限核对**：列标签里背景占 fit 的 **74.6%**，所以"永远判背景"就有 **0.746** 的总体准确率。据此：

- 原文"按列重分组把可解性抬到 0.674"中的 **0.674 低于 0.746**，它不能证明颜色可解，只能证明该编码器的列 token 连"这列有没有颜色"都分不清；
- 正确的分解是：已涂列准确率 **0.369**（已涂列多数类 0.208），背景列 **0.780**（全判背景 0.746）；
- 结论"列 token 仍离上界很远"仍然成立，但理由要换成这条分解，而不是那个总体数。

同一缺陷的后果不止于此：本卡的"加宽到 32"建议建立在"8 维不够"之上，而 P4.1 用 8 维列 token + 逐列颜色监督把四向任务做到 fit **0.906**，直接否掉了这个建议。详见 [P4.1 结果卡](RESULT-TAIJI_U2_P4_1_COLUMN_SUPERVISION_20261114.md) 与 ledger D-20261114-23。
